\textbf{Abstract}\\
This project implements an eight-channel logic analyzer for 3.3~V digital signals
on a Zybo Z7-10 development board. The FPGA samples at up to 100~MS/s, evaluates
level and edge triggers, retains pre-trigger history, and packs raw samples or
transition records. Ordinary scatter-gather DMA transfers the data into DDR
memory. FreeRTOS on the Zynq Cortex-A9 processor manages acquisition, commands,
three configurable live decoder slots, transmission and USB servicing. UART, SPI
and \iu{} decoding is available on the device for live operation and on the host
for recorded captures. The current default connects the Zynq directly to a
Windows computer through USB CDC-ACM. A host-served browser interface provides
waveform viewing, live events, decoding, exports and task traces. Recorded USB
trials transferred 64~MiB as sixteen 4~MiB captures at 1.62~MB/s, with byte-exact
results in three trials. A 60-second UART/SSE test delivered 606,411 events
without client or segment loss. SD boot was verified on 26 September 2026, and
the author confirmed completion of the visual walkthrough. The report
distinguishes FPGA timing, RTOS coordination and transport capacity,
demonstrating the two classes through one integrated instrument.

\section{Hardware in context}

Embedded communication faults are difficult to diagnose from software messages
alone. A UART byte can be wrong because of timing or baud configuration; an SPI
transfer can fail because of clock polarity or chip-select timing; an \iu{}
transaction can fail because an address was not acknowledged. A logic analyzer
records the digital waveforms and associates protocol events with their sample
positions, allowing the signal behavior to be compared with the intended
transaction.

The educational purpose is to combine FPGA design with real-time embedded
software in a working measurement instrument. Commercial instruments such as the
Saleae Logic family and Digilent Digital Discovery provide a useful point of
comparison, while sigrok/PulseView provides a compatible capture-file ecosystem.
This project emphasizes inspectable implementation: custom RTL, register
interfaces, DMA descriptors, RTOS ownership, framed transport and shared
protocol-decoder code.

The earlier project configuration used an ESP32 Wi-Fi gateway. Performance
investigation led to a direct Zynq USB path, which became the default in
September. The gateway remains an optional profile, but it is not needed for the
current instrument or its unified browser interface. The browser runs on the PC
and obtains live events from a PC-hosted bridge.

\subsection{FPGA subsystem}

\begin{figure}[htbp]
\centering
\includegraphics[width=\linewidth]{../assets/figures/02-fpga.png}
\caption{The custom capture logic shares the 100~MHz fabric clock. Sample-rate
division changes the sampling enable. Packing produces 32-bit words, and the
AXI-stream packet boundary tells the DMA when the captured packet is complete.}
\label{fig:fpga}
\end{figure}

\code{la_input_sync} synchronizes the asynchronous input lines before sampling.
The self-test mux selects the internal pattern generator when requested.
\code{la_sampler} implements the configured divider. \code{la_trigger}
evaluates masks and edges, while \code{la_pretrig_ring} preserves samples before
the trigger. The capture controller manages the pre/post window, abort and
overflow response. The raw packer stores four sample bytes in each word; the
transition encoder stores a run count and value. The AXI-stream FIFO accepts
downstream backpressure, and the output marks the final packet beat with TLAST.

The pattern generator provides counter, walking-one, PRBS8, UART, SPI and \iu{}
stimulus. Internal self-test exercises the acquisition pipeline; JE-to-JC
external loopback additionally exercises the physical pads and input
synchronizers. These are distinct validation paths.

The AXI-Lite register source is \path{docs/regmap.yaml}. Its C, SystemVerilog and
Markdown views are generated rather than hand-maintained. The control block is
mapped at 0x40000000 and DMA control at 0x40400000 in the integrated design.

\subsection{DMA, DDR and operating modes}

In burst mode, AcqTask creates a finite descriptor chain, completes the capture
and hands its buffer to the transmitter. The host drains the completed data
after acquisition. In live mode, the FPGA sends transition packets into sixteen
256~KiB segments; completed segments are decoded and returned for reuse. The
default live flush interval is two milliseconds or the configured packet-size
limit, whichever closes the current packet first. Short actual lengths are valid
and are tracked separately from the allocated segment capacity.

Both modes use ordinary scatter-gather descriptors. Live operation reposts
released buffers under software ownership; it does not enable the DMA core's
hardware cyclic mode. DMA descriptors stay non-cacheable. The live payload
region is cacheable in the current build, with explicit invalidation before CPU
readers access memory newly written by DMA.

At 100~MS/s, raw acquisition is 100~MB/s because each sample is one byte. That is
not the sustained PC transfer rate. The current USB drain measurement is
1.62~MB/s, so full-rate acquisition uses finite buffers. Transition encoding
reduces low-transition captures, but its worst case can expand to four bytes per
sample. Loss-free continuous operation is bounded by both decoding and transport
capacity.

\subsection{USB and host subsystem}

The Zynq PS USB0 controller uses the onboard USB PHY and J10 device connector.
CDC-ACM allows Windows to expose the analyzer as a COM endpoint through
\texttt{usbser.sys}. The USB-profile image does not initialize the gateway UART0
link or the PL SPI-bulk service. J12 supplies the documented board
power/JTAG/console path; J10 carries analyzer data.

\code{la-ui} supplies connection controls, captures, waveform viewing, cursors
and edge stepping, host-side recorded-capture decoding, per-slot live control,
exports, offline opening, traces and pattern-generator controls. \code{la-cli}
provides the corresponding scripted operations. Live events come from the
device decoder tasks; decoding an existing capture uses the host native decoder
library. The browser receives events through SSE. One host connection owner
prevents competing operations from claiming the same COM port.

\subsection{Explicit RTOS implementation}

\subsubsection{Why FreeRTOS is used}

FreeRTOS schedules the software pipeline on Zynq CPU0 while the FPGA captures
signals independently. Acquisition management must respond promptly to DMA
completions; decoder tasks must process completed data; the transmitter and USB
task must drain results; command handling must remain responsive to Stop, Abort
and configuration requests. Splitting these activities into tasks makes their
ownership and scheduling explicit rather than combining them in one unbounded
polling loop.

The operating-system tick is one millisecond, not the input sample period. The
FPGA generates sample timing at up to 100~MS/s. FreeRTOS coordinates chunks of
already sampled data, and DMA performs bulk memory writes without requiring the
CPU to copy each input sample.

\code{main.c} checks the reserved memory geometry, applies MMU/cache attributes,
checks the register interface, calls \code{la_app_init()} and starts
\code{vTaskStartScheduler()}. \code{la_app.c} constructs static task control
blocks, stacks, queues and stream buffers. The BSP enables preemption and time
slicing; the project override sets \code{configTICK_RATE_HZ} to 1000. Larger
priority numbers mean greater urgency.

\hline

CmdTask / \code{la_cmd} & 5 & 4~KiB & Parse/validate received frames, route

TxTask / \code{la_tx} & 5 & 12~KiB & Pack burst/live frames, manage
ACK/retransmission state, recycle event blocks and enqueue USB transmission \\ \hline
Decoder slot 0 / \code{la_dec0} & 5 & 4~KiB & Consume its configuration/segment

UsbTask / \code{la_usb} & 5 & 12~KiB & Process USB setup/session work, staged RX

stack-watermark summary on a five-second loop \\ \hline
\end{longtable}

There are eight application tasks in the default USB build, plus FreeRTOS idle
and timer tasks. The three decoder slots are not hard-wired one each to UART, SPI
and \iu{}: any supported configuration can be assigned to a slot, or that slot
can be disabled. Stack constants in \code{la_app.h} count 32-bit stack elements:
1024 elements are 4~KiB, and 3072 elements are 12~KiB. Idle and timer stacks are
separately 2~KiB each.

AcqTask runs at priority 6 to service acquisition before the priority-5 software
consumers. Equal-priority decoder, command, transmitter and USB tasks share
processor time. TxTask was raised from priority 4 to 5 after sustained decoder
production starved the lower-priority consumer. The code also bounds decoder
work to four segments per turn and USB live-event drain to four blocks per turn,
preserving opportunities to process stop and control work.

\subsubsection{Live task-to-task data flow}

\begin{figure}[htbp]
\centering
\includegraphics[width=\linewidth]{../assets/figures/03-rtos.png}
\caption{AcqTask publishes segment handles to configurable decoder slots.
Decoders publish static event-block pointers to TxTask. USB reception reaches
CmdTask through the RX stream buffer. StatusTask is background monitoring; the
figure does not imply that it receives the live payload.}
\label{fig:rtos}
\end{figure}

The processing sequence is:
\begin{enumerate}[leftmargin=1.4em,itemsep=2pt,topsep=2pt]
\item UsbTask feeds incoming bytes to the RX stream buffer. CmdTask parses and
validates each command and sends the acquisition/configuration work to AcqTask
through \code{ctrl_q}.
\item AcqTask starts the live SG chain. The FPGA emits transition words
containing a 24-bit run count and an eight-bit sample value.
\item The DMA interrupt acknowledges completion and notifies AcqTask. AcqTask
collects completed descriptors, checks their actual lengths and invalidates the
DMA-written cache range before a decoder reads it.
\item AcqTask publishes a handle, slot, length and sequence to each enabled
decoder's \code{seg_q}. The large sample payload stays in DDR; the queue does not
copy the entire segment.
\item Each decoder consumes its borrowed segment, feeds the shared C decoding
core and packs output into a static event block. A full block or the
two-millisecond flush check publishes its pointer to \code{ev_q}.
\item TxTask encodes the event frame, places it in the USB TX pool and returns
the event block to \code{block_q}. UsbTask submits ready TX slots in FIFO order;
endpoint completion returns the slot to the pool.
\item After processing the segment, a decoder releases its reference and
notifies AcqTask. Only after all consumer references are released may AcqTask
repost that segment to DMA.
\end{enumerate}

\subsubsection{Ownership, synchronization and queue policies}

\begin{figure}[htbp]
\centering
\includegraphics[width=\linewidth]{../assets/figures/04-ownership.png}
\caption{Hardware ownership and consumer ownership are exclusive. A buffer is
not returned to DMA while any enabled decoder still holds a reference.}
\label{fig:ownership}
\end{figure}

The segment lifecycle is \code{FREE} $\rightarrow$ \code{DMA_OWNED} $\rightarrow$
\code{CPU_OWNED} $\rightarrow$ \code{FREE}. Each segment has generation/sequence
information to reject stale use and detect gaps. AcqTask is the sole descriptor
owner. Consumer release and repost operations use short critical sections to
maintain the live-ring state. Sequence gaps reset a decoder and produce a
discontinuity indication, preventing missing samples from being interpreted as a
continuous bus transaction.

\begin{longtable}{|>{\raggedright\arraybackslash}p{3.2cm}|>{\raggedright\arraybackslash}p{3.1cm}|>{\raggedright\arraybackslash}p{10.4cm}|}
\hline
\textbf{Shared object} & \textbf{Capacity} & \textbf{Full/unavailable policy in the code} \\ \hline
\endhead
\code{ctrl_q} & 4 messages & Zero-wait forwarding; CmdTask logs a full queue. The
USB-session abort send does not check its result. \\ \hline
\code{notice_q} & 8 messages & Zero-wait lifecycle publication; a failed send
does not block acquisition. \\ \hline
\code{tx_q} & 16 small frames & Up to 20~ms wait, then count a TX drop. \\ \hline
\code{ack_q} & 32 messages & Zero-wait send; failure counts a TX drop. \\ \hline
\code{job_q} & 1 burst job & Buffer-busy gate limits the capture buffer to one
job in flight. \\ \hline
\code{cfg_q} per slot & 2 messages & Bounded/zero-wait configuration
publication; no unbounded configuration wait. \\ \hline
\code{seg_q} per slot & 8 handles & Drop only that decoder's attempted reference
and count the drop; expose later sequence gaps. \\ \hline
\code{block_q} & 12 static block pointers & No free block drops/counts the new
event. \\ \hline
\code{ev_q} & 8 filled block pointers & Drop/count the complete new batch and
recycle its block. \\ \hline
USB RX stream buffer & 8~KiB & Retain the current staged input and retry when
the stream buffer is full. \\ \hline
USB RX staging & 16 entries, up to 512 bytes each & Drop the new staging entry
and count overflow when full. \\ \hline
USB TX pool & 16 $\times$ 4160-byte slots & Static counting semaphore reserves
slots; default wait 500~ms, live event/overrun wait 10~ms; failures counted. \\ \hline
\end{longtable}

A FreeRTOS queue safely accepts the three decoder producers. A counting
semaphore represents free USB TX slots, short critical sections reserve slots
atomically, and a ready-index FIFO preserves frame order. The shared frame
sequence counter uses atomic fetch-and-add. Zero-copy describes acquisition
payload handoff to decoders; event packing, transport framing and USB staging
still make bounded copies.

For a burst, AcqTask hands a \code{la_tx_job_t} with the buffer address and
length to TxTask. The buffer-busy gate remains set until the JOB\_DONE
notification. TxTask manages DATA\_BEGIN, DATA\_CHUNK and DATA\_END, the ACK
window, retransmissions and whole-capture CRC. A two-second no-progress timeout
can abandon a stalled transfer and release the job instead of retaining the
capture buffer indefinitely.

\subsubsection{Interrupt work, cache handling and diagnostics}

The PL/DMA handlers in \path{drivers/la_irq.c} acknowledge pending conditions,
record bounded instrumentation and call \code{xTaskNotifyFromISR()}.
\code{portYIELD_FROM_ISR()} requests a context switch when necessary. They do not
perform protocol decoding or CRC processing.

The USB vendor driver has an important bounded-work exception to a simplistic
``all ISRs only notify'' description. Its active endpoint RX callback pops the
completed vendor buffer, copies at most 512 bytes into the sixteen-entry staging
ring, releases that buffer and notifies UsbTask. This matches the vendor
descriptor-cursor requirements. UsbTask performs class/session processing,
stream-buffer delivery, missed-completion sweeps and TX submission. USB IN
completion gives the free-slot semaphore with \code{xSemaphoreGiveFromISR()}.

The application objects are allocated statically with \code{xTaskCreateStatic()},
\code{xQueueCreateStatic()} and related APIs. BSP dynamic-allocation support
remains enabled for its kernel build, but the application task pipeline uses
static storage. The idle/timer memory hooks also supply static stacks.
Stack-overflow and malloc-failure hooks print a fatal diagnostic and halt.

DMA descriptors are non-cacheable. The default live-payload prefix is write-back
cacheable, so AcqTask invalidates each written segment before publication and
TxTask invalidates a completed burst before reading it. The CPU reads these
payloads without writing them. This prevents stale cached samples from being
interpreted as new acquisition data.

StatusTask currently summarizes the watermarks of acquisition, command,
transmission and status tasks, in stack words. It does not include every
decoder/USB watermark. Kernel runtime-statistics generation is disabled; a
CPU-load field alone is not evidence of measured per-task utilization. Custom
trace hooks provide task-switch, queue/stream and DMA/decode/TX markers through a
bounded trace ring that is enabled on request.

\section{Build instructions}

The supported development workflow is native Windows. The main tools are
Vivado/Vitis 2026.1, Questa for procedural RTL simulation, Python 3.11 and
MSVC/CMake/Ninja for portable C checks. The optional gateway uses the pinned
native ESP-IDF installation. \code{python tools/run.py <target>} is the canonical
runner; it resolves the project root from its own script location.

\begin{enumerate}[leftmargin=1.5em,itemsep=2pt,topsep=2pt]
\item Clone the repository, create its \path{.venv} and install the project
package using the setup steps in \path{docs/windows-dev.md}.
\item Check the environment with
\code{python tools/run.py check-env -- --write-lock}.
\item Generate the interfaces with \code{python tools/run.py gen}.
\item Check the software with \code{python tools/run.py test-native} and
\code{python tools/run.py test-host}.
\item Simulate the RTL with \code{python tools/run.py sim} and build the
bitstream/XSA with \code{python tools/run.py bit}.
\item Build the default USB firmware with \code{python tools/run.py fw-zynq}.
\item With the documented power/jumper setup, load the design with
\code{python tools/run.py jtag-zynq}.
\item For SD startup, run \code{python tools/run.py boot}, copy BOOT.BIN to the
FAT32 card root, remove power, set JP5 to SD and power-cycle. \code{package}
stages the profile-aware firmware/host artifacts and hash manifest.
\end{enumerate}

These are reproduction instructions, not a claim that new FPGA/firmware builds
were run during this documentation refresh. The default firmware is USB;
\code{--profile gateway} selects the retained gateway application where
supported.

\subsection{Export and shutdown}

Export \code{.sr} for exact sample-count reopening in PulseView or the UI. VCD
stores transitions and may not preserve a trailing constant run's exact sample
count; the host reports this limitation. Sample CSV contains waveforms, while
event CSV contains decoded annotations. PNG captures the visible waveform region.
Trace controls retrieve the RTOS timeline. Stop live operation, finish/cancel
jobs, disconnect the UI, stop its host server and remove power before rewiring.

All acquisition inputs are 3.3~V only and have no project-added over-voltage
protection. Use an appropriate external level shifter for 5~V logic. Short leads
and common ground are important; synchronization does not guarantee capture of
pulses shorter than the configured sample period.

\subsection{Capabilities and remaining limitations}

\begin{itemize}[leftmargin=1.4em,itemsep=2pt,topsep=2pt]
\item Eight-channel, 3.3~V acquisition is qualified at up to 100~MS/s. The
200~MS/s stretch is unverified and is not part of the current class-project
claim.
\item Burst capacity is bounded by the 8~MiB pool and finite descriptor chain;
oversized captures are rejected rather than silently shortened.
\item UART 115200 and 10~kHz SPI/\iu{} have recorded live gates. High-rate live
workloads can overload decoder/event/transport stages and generate explicit
discontinuity/overrun information.
\item Full-rate raw capture is buffered acquisition, not a 100~MB/s continuous
USB stream. The default host drain measurement is 1.62~MB/s.
\item The optional gateway retains historical Wi-Fi/SPI limitations; its
remaining ESP32-S3 SPI issue and optional tuning are not declared fixed by USB
adoption.
\item The signed-driver-dependent SUMP bridge is deferred. The final v1.0 tag and
public release authorization remain separate from demonstrated operation.
\item The development USB identity is retained for the current in-house setup;
no public product identity or certification is asserted.
\end{itemize}

\section{Conclusion}

The project demonstrates an integrated FPGA and embedded-system instrument: the
FPGA supplies deterministic sampling/trigger/packing, while FreeRTOS provides
explicit scheduling, ownership, live decoding and transport service. The default
USB path replaces the older headline Wi-Fi limitation with a recorded 1.62~MB/s
aggregate drain result. Device live events, host waveform analysis, independent
decoder-slot control, exports, SD startup and the author-confirmed visual
walkthrough complete the documented operating path.

The principal lesson is that sample rate alone does not define an analyzer's
end-to-end capacity. Buffers, descriptor lifetime, decoder throughput, transport
pacing and honest overload reporting must also be designed and verified. The
report shows both classes' contributions through this shared hardware/software
contract while retaining the limits of the measured evidence.
